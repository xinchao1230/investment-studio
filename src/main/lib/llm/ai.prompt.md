# LLM Integration

> Provides model API adapters and LLM-powered utility services (title generation, file naming, MCP config formatting, system prompt writing).

## Key Files
| File | Responsibility | Size |
|------|---------------|------|
| `ghcModelApi.ts` | `GhcModelApi` — primary provider; single-call wrapper over GitHub Copilot `/chat/completions`; `getEndpointForModel()` selects `/chat/completions` vs `/v1/messages` based on model capabilities. Exposes `callModel(...)` (legacy, falls back via `providerManager.resolveModelId` on non-Copilot providers) and `callModelStrict(modelId, ...)` (no silent fallback — throws if the modelId isn't valid for the active provider) | medium |
| `ghcModelsManager.ts` | Model registry (local-cache-first init, background remote refresh with Claude integrity check), capability lookups (`getModelById`, supported endpoints, context window sizes) | ~large |
| `provider/` | Multi-provider router for Copilot, OpenAI, Anthropic (Claude), Google (Gemini), and a single auto-detecting custom endpoint (`custom-dynamic`); owns encrypted per-profile provider config and active-provider model routing. Anthropic is a native provider (`anthropicProvider.ts`) built on the official `@anthropic-ai/sdk`, and Gemini is a native provider (`geminiProvider.ts`) built on the official `@google/genai` SDK — both translate the app's OpenAI-shaped internal types to/from their respective wire formats (Anthropic Messages API; Gemini `generateContent` with `contents`/`role:'model'`/`functionCall`); OpenAI uses raw `fetch` + hand-rolled SSE in `openaiCompatibleProvider.ts`. `custom-dynamic` (`customDynamicProvider.ts`) is a routing wrapper that auto-detects which of the three protocols a user's endpoint speaks (via `protocolDetector.ts`) and delegates to the matching engine | medium |
| `AzureOpenAIModelApi.ts` | Azure OpenAI adapter — reads `PRESET_MODEL_GPT41_*` env vars; single-call, no streaming | small |
| `mcpConfigLlmFormatter.ts` | `McpConfigLlmFormatter` — parses natural language or ad-hoc JSON into a standard MCP server config object via LLM | medium |
| `systemPromptLlmWritter.ts` | `SystemPromptLlmWriter` — direct system-prompt polish flow that preserves user intent, returns polished prompt + change summary, and rejects unusable drafts | medium |
| `chatSessionTitleLlmSummarizer.ts` | Auto-generates chat session titles from first exchange | small |
| `fileNameLlmGenerator.ts` | AI-generated file names for downloads | small |
| `documentSummaryLlmGenerator.ts` | Summarizes document content for context injection | small |
| `contextCompressionLlmSummarizer.ts` | Dedicated compression-summary helper that owns the system prompt, summary template, output language, and prompt-overhead calculation. **Required** `modelId` is passed in by the caller — the helper does not select a model and refuses to invoke the LLM when no `modelId` is provided | small |
| `index.ts` | Re-exports; also exports a singleton `ghcModelApi` instance | tiny |

## Architecture
- **Primary provider**: `GhcModelApi` calls GitHub Copilot's API using the session token obtained from `MainAuthManager`. It is NOT built on Vercel AI SDK — it issues raw `fetch` calls.
- **Streaming** in the main `AgentChat` uses Vercel AI SDK 5.x directly with provider-specific adapters (openai-compatible, google-generative-ai, cohere, ollama). `GhcModelApi` and `AzureOpenAIModelApi` are non-streaming single-call utilities only.
- **Endpoint selection**: `getEndpointForModel()` in `ghcModelApi.ts` prefers `/chat/completions` (OpenAI-compatible) over `/v1/messages` (Anthropic native) to avoid `tool_choice` structure differences.
- **LLM utility classes** (`McpConfigLlmFormatter`, `SystemPromptLlmWriter`, `chatSessionTitleLlmSummarizer`, `contextCompressionLlmSummarizer`) all use `ghcModelApi` internally — they are stateless and do not share instances.
- **`callModelStrict` enforces no-silent-fallback for utility helpers**: `GhcModelApi.callModel(...)` accepts any modelId and, on non-Copilot providers, routes it through `providerManager.resolveModelId(modelId)`, which can silently substitute the provider's configured default, a `PREFERENCE_BY_PROVIDER` family match, or simply the first chat-capable model. That is the right behavior for chat history that may carry stale model IDs across provider switches, but it is the *wrong* behavior for utility helpers and compression — both should run on exactly the user-selected model or fail loudly. `callModelStrict(modelId, userPrompt, systemPrompt?, maxTokens?, temperature?)` is the strict variant: it trims and rejects empty/whitespace modelIds, calls `providerManager.getActiveProvider().validateModel(...)` for non-Copilot providers (and `getModelById(...)` for Copilot) before issuing any request, and throws on mismatch. It never delegates to `resolveModelId`. All five utility helpers (`fileNameLlmGenerator`, `documentSummaryLlmGenerator`, `mcpConfigLlmFormatter`, `chatSessionTitleLlmSummarizer`, `systemPromptLlmWritter`) and the compression path (`contextCompressionLlmSummarizer`, `subAgentContextCompactor.compressToolResult` / `compressEarlyMessages`) call `callModelStrict`. **Do not** introduce new utility helpers that call `callModel` directly — always use `callModelStrict` with a caller-supplied modelId.
- **Utility helpers require a caller-supplied modelId**: All five utility classes (`FileNameLlmGenerator.generateFileName`, `DocumentSummaryLlmGenerator.generateSummary`, `McpConfigLlmFormatter.formatMcpConfig`, `ChatSessionTitleLlmSummarizer.generateTitle`, `SystemPromptLlmWriter.improveSystemPrompt`) take a required `modelId` parameter and refuse to invoke the LLM when it is empty or whitespace, returning a failure-shaped result (the file-naming and chat-title helpers additionally return a deterministic non-LLM fallback name/title so callers always have something to display). The renderer obtains the modelId from `useAgentConfig().currentModel` (current chat's agent model) or — for the agent editor's system-prompt polish — from `cachedData?.model ?? agentData?.model` (the agent being edited's model). The IPC handlers in `startup/ipc/llm.ts` plumb the modelId through to the helper; no IPC handler should fall back to a default model.
- **Compression summary specialization**: `contextCompressionLlmSummarizer.ts` owns the compression-specific system prompt, structured summary template, output language, and prompt-overhead calculation. Its overhead must reflect the real `ghcModelApi.callModelStrict(...)` request shape, including both the system message and the generated user prompt. Callers must supply the `modelId` they want compression to run against (the user's currently selected model); the helper has no fallback model and will refuse to invoke the LLM when `modelId` is empty, returning a failed result so the caller can fall back to truncation. This enforces "no hidden model routing" across providers.
- **Reasoning effort capability**: `getModelCapabilities()` exposes `reasoningEfforts?: string[]` derived from the Copilot `/models` `capabilities.supports.reasoning_effort` array, normalized to lowercase and deduped by `normalizeReasoningEfforts()`. `supportsReasoning` is now `true` whenever any tier is advertised (in addition to the legacy `o3`/`o4` family detection), and `isReasoningModel()` delegates to `supportsReasoning` so both signals stay aligned. Request shaping is performed by `buildReasoningParams({ endpoint, supportedEfforts, reasoningEffort, defaultEffort })`, which produces the OpenAI flat form `{ reasoning_effort }` for `/chat/completions` and the nested form `{ reasoning: { effort } }` for `/responses`; when `reasoningEffort` is omitted (user didn't pick), `defaultEffort` (from `getDefaultReasoningEffort()`) is used so an explicit tier is always sent for models that support reasoning. `getDefaultReasoningEffort(modelId, supportedEfforts)` implements the vendor-aware heuristic: Claude→high, GPT/others→medium. An unsupported or capability-gated tier yields `{}`. New tiers (e.g. `minimal`, `xhigh`) are passed through verbatim — do not whitelist tier names.
- **Provider model limits**: API-key providers derive `ProviderModel.maxContextTokens` and `maxOutputTokens` from real `/models` metadata first, then fall back to `guessContextDefaults(modelId)`. `provider/modelLimitsUtil.ts` owns the shared extractor for finite positive numeric values, including numeric strings and dotted nested paths, and the shared model-name heuristic for current GPT, Claude, Gemini, DeepSeek, Grok, Qwen, GLM, ERNIE, Hunyuan, Doubao, and Seed families. OpenAI-compatible endpoints probe common gateway fields such as `context_window`, `context_length`, `max_context_length`, `max_input_tokens`, `max_model_len`, and OpenRouter-style `top_provider.context_length`; Anthropic-compatible endpoints probe `max_input_tokens`, `context_window`, `context_length`, `max_context_tokens`, plus output-token variants. Both providers log each model's resolved context/output limits and source (`api:<field>` vs `heuristic`), plus a list-level summary showing how many models used API metadata.
- **Compression model is caller-selected, not hardcoded**: `ContextCompressionLlmSummarizer.summarize()` takes a required `modelId` parameter and forwards it directly to `ghcModelApi.callModelStrict(...)`. `FullModeCompressor.compressMessages(messages, modelId)` threads the modelId through every internal helper (`performCompression`, `generateSummary`, `summarizeMessagesRecursively`, the concurrent and sequential chunk workers, `callSummaryAPI`). `AgentChat` supplies its current model via `getCurrentModelId()` so compression always runs on whatever provider/model the user picked — no provider-side preference fallback, no "claude-haiku-4.5" assumption. Tokenizer/budget tuning still targets the previous Haiku reference shape (tokenizer `o200k_base`, `summaryPromptTokenBudget = 100K`, `MAX_TOKENS = 16K`) and remains a reasonable upper bound for most Copilot-served Claude/GPT models; if a user's custom-provider model has materially different limits, errors surface via the existing fallback truncation path.
- Model configurations (provider, model ID, API key, endpoint) are stored per-profile in `profile.json` and managed by `ProfileCacheManager`. The LLM layer reads them at call time, not at startup.
- Multi-provider routing for chat and utility LLM calls is centralized in `provider/ProviderManager`. Provider initialization is serialized per auth/session switch; callers that branch on the active provider must call `waitUntilReady()` first. Skip-login uses the `_local` profile and must only proceed when a non-Copilot provider is enabled and credential-ready.
- **`custom-dynamic` auto-detected protocol**: The single custom-endpoint slot does NOT assume OpenAI. `protocolDetector.ts` (a pure module — no singletons) probes the endpoint's model-listing API in heuristic-prioritized order and returns `{ protocol, normalizedBaseUrl, sampleModels }`. `customDynamicProvider.ts` is a thin router that wraps one instance each of the OpenAI/Anthropic/Gemini engines and delegates every call to the engine matching the detected protocol (remapping each model's `providerId` to `'custom-dynamic'`). Detection runs at two write moments — **Test Connection** and **Save** (`updateProviderConfig` triggers `detect()` when both URL+key exist) — and the verdict is persisted to `provider-config.json` as `ProviderConfig.detectedProtocol` via the manager's `persistDetectedProtocol` callback. At **run time** the saved protocol is loaded and used with zero detection overhead; only a *protocol-shaped* failure (404/405, "messages: required", etc. — NOT 401/429/5xx/timeout) triggers a single re-detect-and-retry (self-heal), and for streaming this only fires before the first chunk is emitted. Each protocol needs a different base-URL shape, so the detector returns a `normalizedBaseUrl` (OpenAI keeps `/v1`; Anthropic/Gemini strip it because their SDKs re-add the version segment) — the provider persists the user's *raw* URL and normalizes per-protocol on the fly. Legacy `custom-openai` configs are migrated to `custom-dynamic` with `detectedProtocol: 'openai'` on load (`migrateLegacyCustomOpenAI`), preserving exact prior behavior with no re-detection.

## Common Changes
| Scenario | Files to Modify | Notes |
|----------|----------------|-------|
| Add a new built-in model | `ghcModelsManager.ts` | Add entry with `supported_endpoints` and context window |
| Add or change an API-key provider | `provider/types.ts` + `provider/providerManager.ts` + provider implementation | Keep provider config encrypted at rest, ensure `resolveModelId()` validates stale chat model IDs before sending requests, and route model-limit extraction through `provider/modelLimitsUtil.ts` instead of hardcoding a single response field |
| Add a new protocol to `custom-dynamic` auto-detect | `provider/protocolDetector.ts` (probe + `normalizeBaseUrl`) + `customDynamicProvider.ts` (`engines` map) | The detector matches a protocol only if its model-listing endpoint returns ≥1 model. Add the new protocol's listing probe, its URL normalization, and an engine instance. Keep the detector pure (no singletons) |
| Point utility LLMs at a different model | `ghcModelApi.ts` constructor (`this.currentModel`) or callers | Default is `gpt-4.1` |
| Add a new LLM-powered utility | Create new file, import `ghcModelApi` singleton from `index.ts` | Follow pattern of `mcpConfigLlmFormatter.ts` |
| Change compression-summary wording, language, or prompt shape | `contextCompressionLlmSummarizer.ts` | Keep `FullModeCompressor` free of helper-specific prompt configuration |
| Change MCP config parsing system prompt | `mcpConfigLlmFormatter.ts` (`SYSTEM_PROMPT` static field) | Hard-coded template |
| Change system prompt writer behavior | `systemPromptLlmWritter.ts` (`SYSTEM_PROMPT` static field) | Keep it as a direct polish flow; do not reintroduce role-description expansion unless the product requirement changes |

## Gotchas
- ⚠️ `ghcModelsManager.initialize(alias)` returns after loading the local cache only — the remote refresh runs in the background. Callers that `await initialize()` must NOT assume the model list is up-to-date from the remote; it may still be the locally cached version. Use `ensureModelsReady()` in IPC handlers to wait for initialization (with timeout), but note that even after it resolves the cache may contain only local data if the remote fetch failed or is still in progress.
- ⚠️ `refreshFromRemote()` has an integrity check: if the remote list is missing Claude models but the local cache has them, the update is rejected to prevent model loss in network-restricted environments (e.g., no VPN). This means the local cache file will NOT be updated in that scenario.
- ⚠️ The file is `systemPromptLlmWritter.ts` (double-t) — this typo is in the source and must be preserved when referencing it.
- ⚠️ `SystemPromptLlmWriter` is intended to polish an existing system prompt draft, not invent a new prompt from a role label. UI copy and validation should reinforce that expectation.
- ⚠️ `GhcModelApi` and `AzureOpenAIModelApi` do NOT use Vercel AI SDK. They issue plain `fetch` calls and return `Promise<string>`. Do not expect streaming responses from them.
- ⚠️ `AzureOpenAIModelApi` throws if `PRESET_MODEL_GPT41_API_KEY` or `PRESET_MODEL_GPT41_ENDPOINT` env vars are empty — it is optional (used only when configured).
- ⚠️ The `McpConfigLlmFormatter` system prompt instructs the model to return pure JSON with no markdown fences. Parsing failures are surfaced via `rawResponse` in the result object.
- ⚠️ `anthropicProvider.ts` is the ONLY API-key provider not built on `openaiCompatibleProvider.ts`. Anthropic's Messages API is not OpenAI-shaped (`system` is a top-level field, content is block-based, streaming uses named events, tool calls are `tool_use`/`tool_result` blocks). It uses the official `@anthropic-ai/sdk` and translates to/from the app's internal OpenAI-shaped `ChatMessage`/`ChatTool`/`ProviderStreamChunk` types. When changing the internal provider types, update this translation too. Anthropic requires `max_tokens` on every request — never send a request without one.
- ⚠️ `customDynamicProvider.ts` contains NO wire-format translation — it is purely a router over the three reused engines. All format logic lives in the engines. When you change the internal provider types, you do NOT need to touch the wrapper, but you DO need to touch each engine.
- ⚠️ `custom-dynamic` self-heal (`shouldSelfHeal`) is a deliberately NARROW allowlist. Re-detection only fires on wrong-protocol signatures (404/405, "messages: required", "not found"). It must NOT fire on 401/403 (auth), 429 (rate limit), 5xx (server), or network/timeout errors — re-detecting those wastes a real chat turn and doubles token spend. The streaming path only self-heals before the first chunk is yielded (retrying mid-stream would duplicate forwarded content). If you widen the allowlist, add a test to `customDynamicProvider.test.ts` asserting the new boundary.
- ⚠️ The `custom-dynamic` provider persists the user's **raw** base URL in `ProviderConfig.baseUrl`, not the normalized one. Normalization is applied per-protocol at configure/detect time via `normalizeBaseUrl()`. Do not persist the normalized URL — a later re-detection must start from the original to probe other protocols correctly.
- ⚠️ **Changing a `custom-dynamic` endpoint must clear the stale `detectedProtocol` verdict.** Settings' Save sends only `{enabled, apiKey?, baseUrl?}` — never the protocol — so in `updateProviderConfig` the `merged = {...existing, ...updates}` would otherwise carry the OLD endpoint's protocol forward. `updateProviderConfig` deletes `merged.detectedProtocol` whenever `baseUrl` or `apiKey` actually changes, forcing a clean re-detect. `detect()` (run on Save) normally re-resolves it, but if that probe fails transiently the cleared verdict prevents the new endpoint from being routed through the previous protocol's engine and showing the previous endpoint's models (the research/chat model dropdown stale-list bug). Belt-and-suspenders: `CustomDynamicProvider.configure()` and `detect()` `dispose()` **all three** inner engines (not just the active one) so no sibling engine retains a prior endpoint's model cache.
- ⚠️ `updateProviderConfig()` (the Settings "Save" path) MUST fire `models:updated` when it reconfigures the **active** provider — otherwise the renderer's `modelCacheManager` never re-syncs and downstream consumers (ModelSelector, research chat) keep showing the stale model list from init/last switch. This bit `custom-dynamic` hardest: saving a new endpoint or flipping the detected protocol (e.g. openai↔anthropic) changes the entire upstream model set, but the chat side showed the old list. The notification is gated to `id === activeProviderId && id !== 'copilot'` so saving a *background* provider's key never swaps the visible list, and Copilot is excluded because `GhcModelsManager` fires its own event. Mirrors the notification logic in `switchProvider()`.
